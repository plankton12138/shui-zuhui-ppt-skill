# 叙事与文案规范：怎么把论文讲成一条线

这份文件决定 PPT 的"含金量"。版式只是壳，壳里的叙事才是听众记住的东西。

## 文案契约：不写水话（最高优先级）

"页标题是论断"指的是**可核对的具体结论**。把一句话打磨得漂亮不算论断。靠对仗、转折、升华撑起来、删掉后信息量不变的句子，一律删。

### 禁用句式

写 `deck.json` 和 `讲稿.md` 时，以下句式一律不许出现：

| 类型 | 命中形式 |
|------|---------|
| 对照式定义 | `不是 A，而是 B`、`并非 A，而是 B`、`问题不在 A，而在 B`、`X 不缺，缺的是 Y`、`缺的不是 A，是 B` |
| 元话语起手 | `一句话：` / `一句话，`、`这页其实就一句话`、`说到底`、`归根结底`、`说白了`、`本质上`、`简单来说`、`值得注意的是`、`众所周知` |
| 空评价 | `关键在于`、`真正的挑战/问题/价值在于`、`这才是`、`显著提升`、`效果显著`、`大幅提升`、`有提升空间`、`值得关注` |
| 口号式对仗 | 两个短分句靠节奏对称、换个抽象名词就能套到任何论文上的句子（如"算力不缺，缺的是够得着"） |
| 破折号升华 | `——这才是…`、`——说白了…`、`——本质上…` |

`不是…而是…` 用于解释技术取舍时偶尔说得通，本 skill 也一律不用：先说被否定的做法具体错在哪，再说论文用了什么，两句各自带事实。

### 改写规则

1. 主语换成论文里的具体名词：部件名、指标名、数据集、基线系统、实验条件。不要用"算力""能力""体验""壁垒"这类大词。
2. 谓语换成可验证的动词：`受限于`、`未覆盖`、`只在…条件下成立`、`比…慢 N 倍`、`需要额外…`。
3. 补上数字、条件、范围或对照组；论文里找不到就删这句，不要拿形容词顶上。
4. 一句只放一个事实，删掉后半句的判断和升华。

| ❌ 水话 | ✅ 改写 |
|--------|--------|
| 算力不缺，缺的是够得着 | 边缘节点需经云端调度器分配；论文测得 EC2 部署约 200 s，同机 OpenFaaS 约 20 s |
| 一句话，不是模型不够大，而是数据没对齐 | 训练语料与评测集的时间窗不重合：语料截止 2023.06，评测覆盖 2024 年 |
| 这页其实就一句话：部署要多久，全看你部署到哪 | EC2 部署约 200 s，OpenFaaS 约 20 s；差在要现装 OpenFaaS 和 Node Exporter |
| 关键在于降低延迟 | 预拉取镜像把冷启动从 200 s 降到 20 s，只对已缓存镜像有效 |
| 真正的挑战是异构 | x86 / ARM / GPU 各用一套部署脚本，现有编排器只支持 x86 |
| 效果显著提升 | 并发从 1 加到 4，反应时间仍在 0–5 s |

封面中文副题同样受此约束：写清论文做了什么、在什么条件下成立，不写对仗口号。

### 自检（必须做）

```bash
python scripts/build_deck.py deck.json -o out.pptx          # 生成时自动拦截
python scripts/build_deck.py 讲稿.md --lint-only             # 讲稿单独扫
```

脚本命中即报错退出。逐条改到 0 命中再交付，不要因为"这句读着还行"就放过。

## 主线原则

**每一页都在回答上一页留下的问题。**

```
这是什么问题 → 现在的方法为什么不行 → 所以他们怎么做的 → 怎么证明有效 → 还有什么没解决
```

写每一页之前先问自己：这一页如果删掉，故事会不会断？不会断就删掉。

## 页标题 = 该页的论断

不要写"研究方法""实验结果"这种栏目名。标题要直接给出结论，让听众扫一眼就知道这页的立场：

| ❌ 栏目名 | ✅ 论断 |
|----------|---------|
| 研究方法 | 研究方法（一）：总体架构 |
| 实验结果 | 实验结果（一）：部署开销由资源类型决定 |
| 实验结果 | 实验结果（二）：SLO 闭环快，开销几乎为零 |
| 结论 | 结论与不足 |

方法页可以中性（因为要讲结构），**实验页必须是论断**。

## 第 2 页：研究背景

四段式，不要写成综述：

1. **背景** —— 大趋势一句带过（IoT/实时应用把计算推向边缘），别展开
2. **特点** —— 为什么难：异构的三个维度（硬件、平台、网络）
3. **目标** —— 作者想让什么东西变成一次调用
4. **两个挑战** —— 直接对应后面方法的两块设计

红字放在"目标"和"挑战"上，因为那是全文的钩子。

反面教材：花半页解释什么是边缘计算。听众都是同行，不需要。

## 第 3 页：研究现状

这一页是"看起来读得深"的关键。结构固定：

```
路线 A：代表工作 1、代表工作 2 → 红字：缺陷
路线 B：代表工作 1、代表工作 2 → 红字：缺陷
路线 C：代表工作 1…3          → 红字：缺陷
────────────────────────────────
共同局限：……（红字收尾，就是本文的立题点）
```

三条硬要求：

- **每条路线必须落到一句缺陷**，缺陷要具体（"不处理 SLO 违约""不支持 serverless"），不要写"仍有提升空间"
- **不要罗列所有 related work**，每条路线 2–3 个足够，剩下的放口播里
- **共同局限要能直接推出本文方法**——写不出这句，说明你还没读懂这篇论文的定位

## 第 4–5 页：研究方法

分两页：**结构** + **动机**。

第 4 页（配架构图）只讲"有哪些部件、怎么连起来"，按层讲，每层一句。不要在这一页解释算法。

第 5 页讲"为什么这么设计"，用编号 ①②③④，每一条对应第 2 页提出的一个障碍：

```
① 统一抽象  ← 解决"平台异构"
② 部署提速  ← 解决"部署太慢"
③ 指标补齐  ← 解决"监控看不到"
④ SLO 闭环  ← 解决"谁来守"
```

这种一一对应关系，是"研究很深"最直接的证据。听众会自己把线连起来。

**不要**在这一页抄公式、列符号表、解释超参数。真要讲，放口播里说一句"具体阈值在论文第 X 节"。

## 第 6 页：实验设置

一页说清四件事，能配测试床表就配表：

- 测试床：几台机器、什么规格、在哪
- 负载：跑的是什么（越简单越要说清"为什么简单"）
- 指标：测了什么
- 场景：几组实验，每组验证什么

红字只标"场景编号"或"指标名"，不要标数字。

## 第 7–8 页：实验结果

**图 + 数字 + 一句机理**。三段式：

```
现象：EC2 启动 ~200 s，比 OpenFaaS 慢一个量级
机理：要现装 OpenFaaS 与 Node Exporter
含义：跨层部署的瓶颈在基础设施准备，不在调度
```

只写现象不写机理 = 念图；只写机理不写数字 = 空谈。两个都要。

红字标**数字**和**反直觉的结论**，不标"显著提升"这种空话。

补充结果页（开销、鲁棒性）可以压到 2–3 条，因为它的作用是"堵住审稿人的嘴"，不是主线。

## 第 9 页：结论与不足

左栏结论 3 条，右栏不足 4–5 条。

不足怎么写才显得懂行：

1. **作者自己承认的**（论文 limitations / future work 段落里）
2. **数据能推出来的**（规模只有 13 个资源、只测了时延类 SLO）
3. **你自己加的评估视角**（基线只有 Python client、没做多租户、没量化重调度期间的中断）

第 3 类最能加分，但要克制——说"如果我来做会先补什么"，而不是"这篇论文很水"。

## 强调色规则（红为主，蓝为辅）

| 该强调 | 不该强调 |
|------|--------|
| 缺陷、gap | 作者名、机构名 |
| 机制名（预拉取、Event Bus） | 泛泛的形容词 |
| 关键数字（200 s、0–5 s、13 个资源） | 年份、卷期号 |
| 反直觉结论（"开销几乎为零"） | 常识性表述 |

红色是默认强调色（缺陷、机制、关键数字）。当需要把**两类同类信息分开**时才引入蓝字——例如"缺陷（红）vs 该路线的优势（蓝）"、"本文方法（红）vs 对照基线（蓝）"。没有区分需求就全部用红，不要为了好看加蓝。

密度：**每页红+蓝合计 1–3 处**。一页全是强调色等于没有重点。

## 长度控制

- 一条 bullet ≤ 45 字，超过就拆成两条或删掉修饰语
- 一页 ≤ 6 条 bullet
- 一页 ≤ 3 个数字
- 页数以讲清为准，通常 8–12 页；每超出一页都要能回答"这页删掉故事会断吗"

写完之后做一次"删一半"测试：随便挑一页，把每条 bullet 的后半句删掉，如果意思没变，那后半句本来就该删。

## 不要做的事

- 不要把摘要翻译一遍当背景页
- 不要按论文章节顺序排（Introduction / Related Work / Method / Evaluation 是写给审稿人的，不是讲给组会的）
- 不要出现"本文将详细介绍"这种过渡句
- 不要出现「文案契约」里列出的禁用句式，包括对仗口号和空评价
- 不要在 PPT 上写"谢谢""请批评指正"
