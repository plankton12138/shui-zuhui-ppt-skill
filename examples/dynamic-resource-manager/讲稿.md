# 讲稿：Dynamic Resource Manager for Automating Deployments in the Computing Continuum

> 全篇 9 页，正常语速约 12–14 分钟。每节的口播可直接照念，括号里是提示，不用念出来。

## 开场（30 秒）

这篇是 arXiv 2024 年 11 月的《Dynamic Resource Manager for Automating Deployments in the Computing Continuum》，因斯布鲁克大学 Samani 团队的工作——他们组之前做过好几篇连续体资源管理的文章。一句话概括：**他们做了一个跑在 Kubernetes 上的资源管理器，把同一份部署请求自动落到云、雾、边三类、四种资源上，并且在 SLO 被违反的时候自己发现、自己纠正。**

---

## P1 封面

**定位**：报题目、报出处、给题眼，不要在这里讲内容。

**口播**：题目直译是"计算连续体中用于自动化部署的动态资源管理器"。关键词有三个：computing continuum、automating deployment、SLO。整篇论文就是围绕这三个词展开的——连续体是场景，自动化部署是手段，SLO 是约束。

**如果被追问**
- Q: 连续体和边缘计算什么区别？ A: 边缘计算只关心近端那一层；连续体强调云—雾—边—端是一个连续的资源谱，应用可以在上面流动。

---

## P2 研究背景

**定位**：交代研究对象和两个挑战，这两个挑战就是后面方法的两块设计。

**口播**：先说对象。现在 IoT 和实时应用把计算从云端往边缘推，结果是云、雾、边、端混在一起，论文管这个叫计算连续体。它难在三个异构：硬件异构、平台异构、网络时延差一个量级。特别是平台——OpenFaaS 是函数、K8s 是容器、Lambda 是 serverless、EC2 是虚机，四套完全不同的运维接口。

所以作者的目标是让"按 SLO 选资源、自动部署、违约重调度"变成一次 API 调用。这自然拆成两个挑战：一是怎么用一个控制面同时驱动四种平台；二是部署完之后，谁来守着 SLO。

**如果被追问**
- Q: 为什么强调平台异构而不是硬件异构？ A: 硬件差异可以用容器抹平，平台差异抹不平——函数、容器、虚机的生命周期模型根本不同。

---

## P3 研究现状

**定位**：说明现有方法为什么接不住这两个挑战，最后落到本文的立题点。

**口播**：现有工作分三条线。

云侧的，Xioadi 他们做了微服务化的管理器，用内存数据网格打破共享存储瓶颈；Aspir 做多云统一层，按客户约束选资源。但都不处理 SLO 违约，也不支持 serverless 和容器化应用。

边缘侧的，Wang 做节点加服务器两级管理器、按优先级准入；Abuibaid 做面向故障恢复的动态重调度。但都缺监控，也没有自动化的基础设施部署。

真正做连续体的有几篇：Morichetta 的意图驱动三层架构、Caballer 的 IaC 加 K8s 编排、Jansen 的多环境部署，还有作者自己之前按 SLO 聚类的工作。但它们普遍不能识别和处理 SLO 违约，有的还不支持 serverless。

合起来看，共同局限很清楚：**要么只覆盖云或边，要么覆盖了全连续体却只支持一种资源类型——异构平台的优势根本用不上。** 这就是这篇论文的立题点。

**如果被追问**
- Q: 为什么不直接用 K8s 联邦调度？ A: 联邦解决的是多集群，不解决跨运行时（函数 / 虚机 / serverless）的统一抽象，也不管 SLO。

---

## P4 研究方法（一）：总体架构

**定位**：只讲结构和连接关系，动机留到下一页。

**口播**：架构是四层解耦。

最下面是持久层，PostgreSQL，只存用户数据和资源、服务、函数的元数据，而且只有核心层能访问。

核心层是主体，用 Eclipse Vert.x 这个响应式框架，七个 Vertex——启动、迁移、数据库、监控、部署、API、告警——通过 Event Bus 用发布订阅、点对点、请求响应三种方式通信。本质是 actor 模型，好处是每个组件可以独立扩缩。

再往上是监控层，用 VictoriaMetrics，它的 MetricsQL 是 PromQL 的超集，兼容 Prometheus 生态，支持拉取和推送，还能做长期存储。

最上面是 GUI，React 加 Next.js，直接内嵌 Grafana 做看板。

**如果被追问**
- Q: 为什么解耦成四层？ A: 要接的平台太多，任何一层写死都会拖死其他层；分层之后换监控后端、换前端都不影响核心逻辑。

---

## P5 研究方法（二）：四个关键设计

**定位**：这页回答"凭什么能做到"，四个设计一一对应背景里的障碍。

**口播**：四个设计，正好对应四个障碍。

第一，**统一抽象**：用 Terraform provider 把 K8s、OpenFaaS、Lambda、EC2 的差异屏蔽掉，一次请求同时创建计算、网络和运行时。

第二，**部署提速**：预拉取镜像，再常驻一个 tiny paused 容器占位，启停服务的时候镜像已经在本地，不用再拉——这是把冷启动成本压下去的关键。

第三，**指标补齐**：监控层拿不到的资源成本、区域时延、K8s Metrics Server 指标，由 Monitoring Vertex 补采，统一转成 OpenTSDB 对象写进 VictoriaMetrics。

第四，**SLO 闭环**：Alerting Vertex 周期校验资源的真实状态，一旦违约就往客户端注册的 HTTP 端点推告警，触发重新分配资源。

**如果被追问**
- Q: 预拉取会不会浪费资源？ A: 用的是 tiny paused 容器，占用极小，论文的说法是 minimize resource usage。
- Q: 为什么不直接读 Prometheus？ A: 它需要长期存储和跨区域聚合，VictoriaMetrics 更省、更快，而且 MetricsQL 兼容 PromQL，迁移成本低。

---

## P6 实验设置

**定位**：一页说清测试床、负载、指标、场景。

**口播**：测试床是真的跨三层的：边缘三台，一台 Intel NUC 加两个树莓派，跑 OpenFaaS；雾是一个七节点的 K8s 集群；云上是 AWS 的 EC2 t2.large 和 Lambda，分别在 us-east-1 和 us-west-2。

负载故意做得很简单——一个睡一秒的 Python 函数、一个立即返回的函数、一个 nginx 容器服务。这是有意的：**他们要测的是管理器本身的开销，不是应用性能。**

指标五个：部署与终止时延、响应时间、CPU 内存占用、SLO 反应时间、函数调用 RTT。三组场景正好对应这三类指标。

**如果被追问**
- Q: 为什么负载这么简单？ A: 变量控制。负载一复杂，测出来的时延就分不清是管理器还是应用本身。

---

## P7 实验结果（一）：部署开销由资源类型决定

**定位**：主结果，说明跨层部署的瓶颈在哪。

**口播**：Fig.2 和 Fig.4 一起看。

部署时间几乎完全由资源类型决定，量级差十倍：OpenFaaS 最快，十几秒；K8s 次之；Lambda 明显慢，跨区网络加更复杂的初始化；**EC2 最差，启动两百秒、终止六十五秒**——原因写得很实在，要现装 OpenFaaS 和 Node Exporter。

并发上去之后部署时间还会涨，因为要拉镜像、初始化容器，但终止时间基本不变。

Fig.4 是资源占用：OpenFaaS 和 K8s 很轻，Lambda 和 EC2 明显更吃 CPU 和内存，因为 AWS 的 Terraform provider 本身更重。

所以这页的结论是：**跨层部署的代价主要不在调度，而在基础设施准备。**

**如果被追问**
- Q: 200 秒是不是太夸张？ A: 这是 EC2 从零装 OpenFaaS 加 Node Exporter 的冷启动代价，属于极端情况；镜像预热过会快很多。

---

## P8 实验结果（二）：SLO 闭环快，开销几乎为零

**定位**：证明闭环有效，同时证明自己不是负担。

**口播**：Fig.5 是 SLO 闭环的证明。纵轴是反应时间，最高才 5 秒，中位数在 2 秒上下；而且并发从 1 加到 4，箱子几乎没变形——说明违约能被快速发现，且不受部署负载影响。

Fig.6 是开销的证明：函数调用 RTT 和管理器直连、裸 Python HTTP client 基本持平，甚至略低，说明**管理器本身几乎不引入额外开销**。

要注意 12 并发以后 EC2 和 OpenFaaS 的 RTT 抬头，那是 CPU 核数限制，不是管理器的问题；Lambda 因为按设计可弹性扩展，反而没这个问题。

**如果被追问**
- Q: RTT 比裸客户端还低，可信吗？ A: 差距在误差范围内，论文的结论是 "lower or roughly equivalent"，重点是证明没有显著 overhead。

---

## P9 结论与不足

**定位**：收口，并给出自己的判断。

**口播**：结论三句：在 K8s 之上用 Vert.x 实现了跨云雾边的资源管理器；四层解耦加 IaC，让同一份请求能落到四类资源；真实测试床验证了部署可自动化、SLO 违约可发现、附加开销可忽略。

不足我挑两条说。一是**规模**：整个测试床就 13 个资源、一个集群，多租户和大规模压力都没做。二是**SLO 维度**：只验证了时延，吞吐、成本、可用性以及它们之间的权衡都没碰。

另外三条在 PPT 上：事后响应而非预测、基线只有 Python client、依赖 IaC 导致 EC2 部署仍然很贵。

如果接着做，我会先把成本维度加进去——连续体场景里，钱和时延往往是反着走的。

**如果被追问**
- Q: 这篇能直接用到生产吗？ A: 架构可以，但生产要多租户隔离、配额、故障自愈，这些论文没展开。
- Q: 和作者前一篇有什么区别？ A: 前一篇是按 SLO 聚类降浪费，不支持 serverless；这篇补上了 serverless 和跨平台部署。
